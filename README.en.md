VibeDrop consists of three components that communicate directly over the local network through **WebSocket**, requiring neither the internet nor a cloud service:

- **Mac desktop app** (`desktop/`) — receives text/files, broadcasts the clipboard, and provides the system tray integration
- **Mobile app** (`mobile/`, Android + iOS) — sends text/images/videos/files and provides the history timeline
- **Home Vault** (`scripts/`) — home server for cross-device history merging, original-media storage, and probe-log collection

## Technical Architecture Overview

```
        ┌────────────────────────────┐      ┌────────────────────────────┐
        │   Mac 桌面端 × N (Tauri 2) │      │  手机端 × N (Tauri 2 Mobile)│
        │  ├ Axum HTTP/WS :9001      │◄────►│  ├ app.js  单文件前端       │
        │  ├ enigo 键盘模拟          │  WS  │  ├ lib.rs  16 个原生命令    │
        │  ├ arboard 剪贴板监听      │      │  ├ Kotlin  保活/播放器/剪贴板│
        │  ├ CGEventSource 活动上报  │      │  └ iOS     滚动锁(KVO)      │
        │  └ UDP/HTTP 发现应答       │      └──────────────┬─────────────┘
        └──────────────┬─────────────┘                     │
                       │              HTTP :8788           │
                       ▼                                   ▼
        ┌──────────────────────────────────────────────────────────┐
        │        Home Vault (家庭服务器, home-vault-receiver.py)     │
        │  跨设备历史合并 · 媒体原件仓(哈希去重+Range) · SSE 广播     │
        │  设备名公告板 · 探针日志回收 · 自我研究报告(SWR)            │
        └──────────────────────────────────────────────────────────┘
```

There are three communication paths, all direct over the LAN and independent of the cloud:

1. **Phone ↔ Mac**: WebSocket (`:9001/ws`) transfers text/files/clipboard data and activity queries after PIN authentication;
2. **Every endpoint → Home Vault**: HTTP (`:8788`) pushes incremental history and media uploads and retrieves reports;
3. **Vault → clients**: a persistent SSE connection (`/api/events`) broadcasts immediately after data is persisted and sends a heartbeat every 25 seconds.

## Core Flows in Detail

### Smart Send Card “Follow-Cursor Send”

1. When the desktop app receives `activity_query`, it calls `CGEventSourceSecondsSinceLastEventType`
   (zero permissions and zero threads—it reads the existing ledger maintained by the system for the screen saver) to answer “how many seconds since the last keyboard or mouse activity”;
2. The phone polls every connected Mac once per second and compares their **relative idle seconds** (immune to clock differences between machines).
   The freshest one is the Mac with the cursor: Universal Control delivers real keyboard and mouse events to that machine, so the signal is tightly coupled to the fact being inferred;
3. The target is locked at the instant text, images, or files are sent; tapping the indicator cycles between automatic and manual modes.

### Discovery and Pairing

The phone scans along two paths in parallel: UDP broadcast + HTTP probing (`discover_desktops`). Once it discovers the desktop app, it starts verification-code pairing (the desktop shows a pending-confirmation card and both sides compare the same code); after approval, the device is saved and connected automatically.
After a custom device name is saved, the Vault bulletin board (`/api/device-names`, keyed by serverId, LWW) synchronizes it across phones.

### Text and Files

- Text: the `type` / `type_enter` actions make the desktop app simulate typing through enigo; Away Mode instead uses
  `clipboard_text` (clipboard-only, for use with remote-control tools such as UU Remote);
- Files: a chunked-transfer protocol (begin/append/finish/cancel) delivers items to the mobile Inbox or Photos;
  drag and drop or a Finder service sends from the Mac. A `transferId` follows every transfer end to end so the sending and receiving records can be merged precisely;
- Send buttons refuse focus capture (mousedown preventDefault), so keyboard and voice-input sessions remain active after sending,
  enabling continuous dictation with no extra actions.

### History Sync (Incremental + Real-Time)

- Each endpoint keeps local history plus a push cursor (`lastPushedEntryId`) and pushes only increments (measured at 3 ms/188 B for one entry);
- Vault merges the all-device timeline (`/api/history/merged`). Clients normally fetch a lightweight 2,000 entries and perform one deep 10,000-entry fetch per session; an SSE event refreshes the view immediately;
- Identical names are merged automatically (a reinstall's new random ID, its “past life,” folds into the local identity); names are presentation, while identity relies on fingerprints.

### Original-Media Store

Originals enter the store by SHA-256 (`/api/media/upload`, streaming + deduplication, 2 GB limit). Any device can retrieve an original online by hash (`/api/media/blob/<hash>`, with Range streaming)—“missing locally ≠ missing everywhere.”

### Startup Self-Test Probe (Black Box)

The top of `app.js` installs window.onerror capture plus probe() instrumentation. Six seconds after startup, or 1.5 seconds after an error, it sends a POST to Vault `/api/client-log`, which persists logs per device. Do not guess at real-device black/white-screen failures; locate them from the logs.

## Platform Lessons Learned

### WebView Engine Differences (Important)

| | Android | iOS | macOS Desktop |
|---|---------|-----|-----------|
| Engine | Chromium | **WKWebView** | **WKWebView (same as iOS!)** |
| `content-visibility: auto` | ✅ Native virtualization | ❌ Black screen | ❌ Blank while scrolling |
| Long-list strategy | content-visibility | JS virtual scrolling | Chunked mounting |
| Chinese segmentation with `Intl.Segmenter` | ❌ Splits into individual characters | ✅ Full dictionary | ✅ |

**Conclusion: cross-engine Chinese segmentation must use server-side jieba; content-visibility is allowed only on Android.**

### iOS

- **Fixed layout**: the outer WKWebView's scrolling is disabled by application-shell design (`isScrollEnabled=false` blocks gestures only;
  WebKit's keyboard reveal uses programmatic scrolling, so **KVO must also observe contentOffset and reset it before rendering**;
  the pinned “origin” is the system's resting position at `-adjustedContentInset`, not (0,0)); reinstall the lock whenever the app returns to the foreground;
- Packaging rule: `cargo tauri ios build --export-method debugging`; do not use Xcode Run directly;
- Free signing remains valid for 7 days (counted from the creation date) and needs an automated re-signing pipeline.

### Android

- A custom WebChromeClient **must delegate to the original client** (onShowFileChooser, etc.); replacing it wholesale silences the file picker;
- The real console is available through `adb logcat -d VibeDropConsole:I "*:S"`;
- The five “Cannot redefine property” errors at startup are harmless noise from Tauri's injected script running twice; do not investigate them.

### Mac

- enigo keyboard simulation runs on a dedicated thread; the clipboard is polled every 500 ms → broadcast channel → each WS connection;
- The desktop binary's internal name is still `voicedrop` (remember this when using pgrep).

## Languages (i18n)

The project follows the gettext model: **the Chinese source text is the key**. `t('发送并回车')` looks up the current-language dictionary, and a missing translation falls back to the Chinese source text (so a partially translated build is always releasable). Use placeholders for variables, as in `t('已改名为 {name}', {name})`; string concatenation is forbidden.
There are currently 11 languages. Adding a language means one `locales/<lang>.json` file plus one line in the `i18n.js` mapping table.

- Quality gate: `python3 scripts/i18n-check.py --strict` (key coverage/placeholder integrity);
- Semantic acceptance: manually review 30 core terms in every language (machines cannot guarantee semantics; see `docs/i18n-规范.md`);
- Names in the language selector use each language's **self-name** with Chinese and English pronunciation aids, and no language pack translates them.

## Build and Deployment

```bash
# Android(需 cargo + Android SDK 于 PATH)
./scripts/deploy-android.sh          # 构建签名 APK + adb 安装启动

# macOS 桌面端
./scripts/deploy-desktop.sh          # 构建 + 本地自签 + 装入 /Applications
#   --skip-build --skip-icons        # 复用现成产物只重装(异机编译后拷贝场景)

# iOS(必须走 Tauri 管线)
cd mobile/src-tauri && cargo tauri ios build --export-method debugging
xcrun devicectl device install app --device <UDID> gen/apple/build/arm64/VibeDrop.ipa
```

**Two rules**:

1. After app.js / index.html / style.css / i18n.js / locales/ in `mobile/src/` changes,
   it **must be copied to `desktop/static/`** (the desktop HTTP service's mobile-browser version);
2. **The two Tauri builds cannot run concurrently** (they share a local IPC channel and will collide); they must run serially.

## message self study and Word-Frequency Report

Analyze your own Home Vault history corpus for segmented-word frequencies, catchphrases, frequent phrases, monthly topic evolution (TF-IDF), and send trends (hour/day-granularity bar charts with finger scrubbing for details). The result is a self-contained HTML report; all processing stays local and no data is sent out.

**View it directly in the app**: History → “message self study” card → Open full report (Home Vault endpoint `/report/self-study`; SWR cache opens instantly, expired reports are recomputed in the background, and `?refresh=1` forces a rerun).

You can also generate it manually:

```bash
python3 -m venv .venv && .venv/bin/pip install jieba
.venv/bin/python scripts/message-self-study.py http://<你的vault地址>:8788
```

The report is written to `~/Downloads/`. See `docs/i18n-规范.md` for the multilingual implementation contract.
